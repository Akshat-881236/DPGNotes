Cloud Firestore Real-Time Database & Data Modeling

19 min read Production-Verified DRASA Engineering Standard

Data persistence in DPGNotes is engineered on Google Cloud Firestore multi-region clusters (eur3), delivering automatic horizontal partitioning, sub-50ms read latency, and real-time reactive UI hydration via WebSockets. To support high-velocity academic operations across 8 study disciplines without race conditions, DPGNotes employs a battle-tested relational NoSQL document schema, atomic counter transactions, role-based security rules, and selective data denormalization.

1. Architectural Scope & Software Requirements Specification (SRS)

Subsystem Directive: Relational NoSQL Schema Design, Concurrency Control & Declarative Security Governance.

The Software Requirements Specification (SRS Section 5.0) mandates guaranteed data consistency for student metrics, verified contributor reputations, and ephemeral resource links. All database read and write pathways must execute in under 50ms, maintain zero document write conflicts during concurrent student exam surges, and enforce strict institutional privacy by isolating confidential administrative records from public queries.

Operational Invariant & Acceptance Criteria
All modifications to numeric metrics (view counts, document download tallies, contributor upvotes) must execute via atomic Firestore FieldValue.increment(1) operations or inside isolated runTransaction() closures. Direct read-modify-write patterns on the client are strictly prohibited by Firestore Security Rules to eliminate dirty writes and race conditions.

2. Component Hierarchy, ER Diagram & Multi-Tier Connectivity Workflow

The DPGNotes data model orchestrates six specialized root collections and subcollections across the multi-tier platform architecture:

  • 1. users (Root Collection): Stores unified student and contributor profiles, indexed by Firebase Auth uid, including verified roles (guest, contributor, admin), department affiliation, and gamified reputation points.
  • 2. documents (Root Collection): Holds study material metadata across the 8 academic categories (SE, SP, UE, EV, T&N, IQ, A&LR, PQ). Contains denormalized contributor display names to eliminate expensive client-side joins.
  • 3. share_links (Root Collection): Maps ephemeral, tamper-resistant 8-character alphanumeric tokens to destination notes, videos, or solutions with view counters and expiration timestamps.
  • 4. videos (Root Collection): Catalogues YouTube tutorial references, embedded lecture notes, and sponsored interstitial metadata for the Educational Media Studio.
  • 5. confidential_requests (Protected Collection): Holds contributor access requests and justifications. Strictly guarded by Firestore Security Rules—unauthorized client read attempts are rejected at the database level.
  • 6. engagement_logs (Telemetry Collection): Captures anonymous reading telemetry, search query frequencies, and device viewport categories to feed the platform's SERP ranking algorithms.

3. Step-by-Step Production Implementation Guide

Follow the practical engineering roadmap to configure and query the DPGNotes Cloud Firestore database:

  1. Define Firestore Security Rules: Author declarative rules asserting that unauthenticated clients cannot read confidential_requests, while permitting public reads for verified documents.
  2. Deploy Composite Indexes: Build composite indexes in firestore.indexes.json supporting multi-attribute queries such as discipline == 'BCA' && category == 'SE' && createdAt >= [timestamp] ordered by views DESC.
  3. Implement Atomic Concurrency Counters: Utilize FieldValue.increment(1) when recording student views on notes to prevent high-traffic write collision errors.
  4. Bind Real-Time Snapshots: Attach onSnapshot() in Vanilla JavaScript modules to instantly update UI elements when notes receive community verification or upvotes.
  5. Feed Automated SEO Sitemap Pipelines: Query active document documents via Node.js batch scripts to dynamically generate sitemap.xml with canonical links and freshness dates for search engines.

// Module 5: Firestore Concurrency Transaction & Atomic Engagement Counter
const admin = require('firebase-admin');
const db = admin.firestore();

/**
 * Atomically increments document engagement and awards contributor reputation points
 * inside a single isolated Firestore transaction to eliminate race conditions.
 */
async function recordDocumentEngagement(docId, studentUid) {
  const docRef = db.collection('documents').doc(docId);
  const logRef = db.collection('engagement_logs').doc();

  try {
    const result = await db.runTransaction(async (transaction) => {
      const docSnapshot = await transaction.get(docRef);
      if (!docSnapshot.exists) {
        throw new Error('Target academic document not found in Firestore.');
      }

      const docData = docSnapshot.data();
      const uploaderUid = docData.uploaderUid;
      const uploaderRef = db.collection('users').doc(uploaderUid);

      // 1. Atomically increment document view count
      transaction.update(docRef, {
        views: admin.firestore.FieldValue.increment(1),
        lastAccessedAt: admin.firestore.FieldValue.serverTimestamp()
      });

      // 2. Award reputation point to the verified contributor (1 point per 10 views)
      if (docData.views % 10 === 0) {
        transaction.update(uploaderRef, {
          reputation: admin.firestore.FieldValue.increment(1)
        });
      }

      // 3. Record audit log
      transaction.set(logRef, {
        docId: docId,
        studentUid: studentUid || 'anonymous_guest',
        timestamp: admin.firestore.FieldValue.serverTimestamp(),
        category: docData.category
      });

      return { newViewCount: docData.views + 1 };
    });

    console.log(`[FIRESTORE] Engagement logged atomically for ${docId}:`, result);
    return result;
  } catch (err) {
    console.error('[FIRESTORE-TRANSACTION-ERROR]', err.message);
    throw err;
  }
}

module.exports = { recordDocumentEngagement };
