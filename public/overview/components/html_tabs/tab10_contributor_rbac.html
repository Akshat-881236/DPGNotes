Contributor RBAC, Authentication & Identity Security

19 min read Production-Verified DRASA Engineering Standard

Academic collaboration requires granular authorization boundaries that separate public student readers from verified content creators and institutional administrators. DPGNotes implements a unified multi-provider authentication architecture supporting Google OAuth, GitHub OAuth, and institutional Student ID/Email credentials. This is governed by an asymmetric RS256 JWT claim verification engine, an automated reputation scoring ledger, and a silent, tamper-proof administrative clearance gate that operates purely behind the scenes without polluting the document presentation layer.

Core Tech: Firebase Auth & RS256 JWT Multi-Provider SSO Role-Based Access Control Silent Clearance Gate Shared Auth Modals Custom Claims Firestore Security Rules Reputation Scoring

1. Architectural Scope & Software Requirements Specification (SRS)

Subsystem Directive: Multi-Provider Credential Parity, Hierarchical RBAC & Silent Administrative Governance.

The Software Requirements Specification (SRS Section 10.0) mandates seamless identity parity: whether a student signs in via Google, GitHub, or direct Student ID and password, all sessions resolve to a single authoritative Firestore document (users/{uid}). Contributor roles grant write access to designated academic folders, while elevated administrative operations require active clearance verification recorded in confidential_requests/{uid}.

Operational Invariant & Acceptance Criteria
Clearance authorization checks must execute strictly in memory and within the Firestore security layer. In compliance with DRASA confidentiality directives, no visual clearance threshold badges, expiration timestamps, or admin approval metrics are rendered into the client DOM tree. The authorization layer exists and enforces boundaries silently.

2. Component Hierarchy & Identity Verification Topology

The authentication and access control subsystem is structured into four decoupled layers:

  • 1. Unified Shared Auth Component (/auth-component.js): Provides modal dialogs across all platform pages (window.dpgLoginGoogle, window.dpgLoginGithub, window.openSignInModal, window.openSignUpModal), firing uniform dpg-auth-success custom events upon token issuance.
  • 2. Asymmetric JWT Claim Verifier (Firebase Admin SDK): Inspects incoming Bearer tokens, validates RS256 digital signatures against Google certificates, and unpacks custom claims (role: "contributor").
  • 3. Silent Clearance Gate Engine: Checks user approval records against Firestore confidential_requests/{uid}. When authorized, access is granted seamlessly without altering the public UI layout.
  • 4. Contributor Gamification & Reputation Engine: Awards community reputation points for verified uploads (+25 points) and approved solutions (+10 points), while deducting points for flagged inaccuracies.

3. Step-by-Step Production Implementation Guide

Follow the practical engineering roadmap to configure and enforce RBAC within the DPGNotes architecture:

  1. Mount Shared Auth Component: Include <link rel="stylesheet" href="/auth-component.css"> and <script type="module" src="/auth-component.js"></script> in the document head.
  2. Listen for Authentication Events: Attach a global listener for the dpg-auth-success CustomEvent to automatically re-evaluate clearance state without page reloads.
  3. Implement Silent Clearance Verification: Query db.collection('confidential_requests').doc(user.uid) in JavaScript. If status === 'approved', hide the gate overlay and proceed with content mounting.
  4. Enforce Backend RBAC Middleware: Write an Express middleware verifying that req.user.role equals contributor or admin prior to allowing document mutations.
  5. Secure Cloud Firestore Rules: Write security rules verifying request.auth != null and matching the document's uploaderUid to prevent unauthorized document edits.

// Module 10: Express RBAC Middleware & Silent Clearance Validator
const admin = require('firebase-admin');
const db = admin.firestore();

/**
 * Middleware enforcing verified Contributor or Admin RBAC claims
 */
async function requireRole(allowedRoles = ['contributor', 'admin']) {
  return async (req, res, next) => {
    const authHeader = req.headers.authorization;
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
      return res.status(401).json({ error: 'Authentication required.' });
    }

    const token = authHeader.split('Bearer ')[1];
    try {
      const decodedToken = await admin.auth().verifyIdToken(token);
      req.user = decodedToken;

      // Query user record for authoritative role
      const userDoc = await db.collection('users').doc(decodedToken.uid).get();
      if (!userDoc.exists) {
        return res.status(403).json({ error: 'User record not initialized.' });
      }

      const userData = userDoc.data();
      const userRole = userData.role || 'guest';

      if (!allowedRoles.includes(userRole)) {
        return res.status(403).json({
          error: 'Access denied: Contributor privileges required.',
          currentRole: userRole
        });
      }

      req.userRole = userRole;
      next();
    } catch (err) {
      return res.status(401).json({ error: 'Invalid or expired session token: ' + err.message });
    }
  };
}

/**
 * Silent Clearance Validator: Evaluates admin approval without leaking dates or badges to DOM
 */
async function checkSilentClearance(uid) {
  try {
    const reqDoc = await db.collection('confidential_requests').doc(uid).get();
    if (!reqDoc.exists) return { authorized: false, reason: 'NO_RECORD' };

    const data = reqDoc.data();
    if (data.status === 'approved') {
      return { authorized: true };
    }
    return { authorized: false, reason: data.status || 'PENDING' };
  } catch (err) {
    console.error('[CLEARANCE-ERROR] Silent check failed:', err.message);
    return { authorized: false, reason: 'SYSTEM_ERROR' };
  }
}

module.exports = { requireRole, checkSilentClearance };
